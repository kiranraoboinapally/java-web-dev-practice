# 00.02.2 — Linux Users & Permissions

Now we move to the next Linux foundation.

The goal is to understand **who can do what on a Linux machine**.

This is extremely important on servers because Linux is designed for multiple users and does not allow every user to freely modify everything.

---

# 1. Why Do We Need Users?

Imagine one Linux server is used by:

```text
Alice
Bob
Admin
```

All three can log in to the same computer.

Should Alice be able to:

* Delete Bob's files?
* Change system configuration?
* Install anything she wants?
* Shut down the server?
* Modify security settings?

Usually, **no**.

So Linux needs a way to identify users and control what they are allowed to do.

That's where:

```text
Users
Groups
Permissions
```

come in.

---

# 2. What Is a User?

A **user** is an identity recognized by Linux.

For example:

```text
student
admin
developer
root
```

When you log in as:

```text
student
```

Linux knows:

> "This person/process is operating as the `student` user."

That identity is then used when deciding access to files and other resources.

---

# 3. Your Lab Example

In your lab environment, you were given a standard account:

```text
username: student
password: student
```

and:

```text
root
password: redhat
```

So conceptually:

```text
Linux machine
     |
     +--- student
     |
     +--- root
```

`student` and `root` are two different user identities.

---

# 4. What Is `root`?

`root` is the Linux **superuser**.

It has very high privileges over the system.

Think of:

```text
student
   ↓
normal user
   ↓
limited access

root
   ↓
superuser
   ↓
very broad system access
```

A normal user might not be allowed to modify:

```text
/etc/...
```

But `root` generally can.

---

# 5. Why Is `root` Powerful?

Suppose you run:

```bash
rm important-file
```

as a normal user.

Linux checks:

> "Does this user have permission?"

If not, the operation fails.

But `root` has special privileges and can perform many operations that normal users cannot.

That's why you should treat `root` carefully.

A mistake as a normal user might affect your own files.

A mistake as `root` can affect the entire machine.

---

# 6. How Does Linux Identify a User?

Internally, Linux assigns users a number called a:

# UID

UID means:

> **User ID**

For example:

```text
student → UID 1000
```

The exact UID can vary.

You don't normally need to remember the number.

The important idea is:

```text
Username
   ↓
UID
   ↓
Linux's internal user identity
```

---

# 7. See Your UID

Run:

```bash
id
```

You might see:

```text
uid=1000(student) gid=1000(student) groups=1000(student)
```

For now focus on:

```text
uid=1000(student)
```

This means:

```text
UID     = 1000
Username = student
```

---

# 8. What Is a Group?

A **group** is a collection of users.

Suppose:

```text
Developers
    |
    +--- Alice
    +--- Bob
    +--- Charlie
```

Instead of giving Alice, Bob, and Charlie permissions individually, Linux can give permissions to the **Developers group**.

Then:

```text
Developers group
       ↓
Permission to access project
       ↓
Alice
Bob
Charlie
```

This makes administration much easier.

---

# 9. Why Do We Need Groups?

Imagine 50 developers need access to:

```text
/opt/project
```

Without groups, you might have to manage permissions for 50 users individually.

With groups:

```text
developers
    |
    +--- user1
    +--- user2
    +--- user3
    +--- ...
```

You can assign access to:

```text
developers
```

instead.

Then members of that group receive the appropriate access.

---

# 10. What Is a GID?

Just like users have a UID, groups have a:

> **GID — Group ID**

So:

```text
User
 ↓
UID

Group
 ↓
GID
```

Again, don't memorize the numbers.

Understand what they represent.

---

# 11. User + Group

A user can belong to one or more groups.

For example:

```text
student
   |
   +--- students
   +--- developers
   +--- docker-users
```

This means the `student` user can inherit permissions associated with those groups.

---

# 12. Now the Important Part: File Ownership

Remember our previous section:

```text
linux-lab/
├── notes.txt
└── backup/
```

Linux doesn't just know:

> "This is a file."

It also keeps information about:

```text
Who owns it?
Which group owns it?
What permissions exist?
```

For example:

```bash
ls -l
```

might show:

```text
-rw-r--r-- 1 student developers 120 notes.txt
```

The important part is:

```text
student developers
```

Meaning:

```text
Owner = student
Group = developers
```

---

# 13. Three Permission Categories

Linux permissions are primarily considered for:

```text
Owner
Group
Others
```

Think:

```text
File
 |
 +--- Owner
 |
 +--- Group
 |
 +--- Others
```

For example:

```text
student → owner
developers → group
everyone else → others
```

---

# 14. Three Basic Permissions

Linux uses three basic permission types:

```text
r
w
x
```

They mean:

```text
r = read
w = write
x = execute
```

So:

```text
Read
Write
Execute
```

---

# 15. What Does Read Mean?

For a normal text file:

```text
r
```

means the user can read/view its contents.

For example:

```bash
cat notes.txt
```

requires appropriate read access.

Think:

> **Read = can I look at the contents?**

---

# 16. What Does Write Mean?

```text
w
```

means the user can modify the file.

For example, writing new content into a file requires appropriate write permission.

Think:

> **Write = can I change the contents?**

---

# 17. What Does Execute Mean?

```text
x
```

means the file can be executed as a program/script when other requirements are met.

For example:

```text
script.sh
```

may need execute permission to be run directly.

Think:

> **Execute = can this file be executed?**

We'll go deeper into this later.

---

# 18. Understanding `ls -l`

This is where everything starts connecting.

Run:

```bash
ls -l
```

You might see:

```text
-rw-r--r-- 1 student developers 120 notes.txt
```

Let's break it apart.

```text
-rw-r--r--
```

contains the permission information.

Then:

```text
student
```

is the owner.

Then:

```text
developers
```

is the group.

---

# 19. Breaking Down `-rw-r--r--`

This looks scary at first:

```text
-rw-r--r--
```

But it is actually structured.

```text
- rw- r-- r--
  |   |   |
  |   |   +--- Others
  |   +------- Group
  +----------- Owner
```

The first character:

```text
-
```

indicates this is a regular file.

Then:

```text
rw-
```

belongs to the owner.

Then:

```text
r--
```

belongs to the group.

Then:

```text
r--
```

belongs to others.

---

# 20. So What Does `rw-` Mean?

For the owner:

```text
rw-
```

means:

```text
r → read
w → write
- → no execute
```

So the owner can:

```text
Read   ✓
Write  ✓
Execute ✗
```

---

# 21. What Does `r--` Mean?

```text
r--
```

means:

```text
r → read
- → no write
- → no execute
```

So:

```text
Read    ✓
Write   ✗
Execute ✗
```

---

# 22. Full Example

Consider:

```text
-rw-r--r--
```

It means approximately:

| Who    | Read | Write | Execute |
| ------ | ---- | ----- | ------- |
| Owner  | ✅    | ✅     | ❌       |
| Group  | ✅    | ❌     | ❌       |
| Others | ✅    | ❌     | ❌       |

So:

> Owner can read/write. Group can read. Everyone else can read.

---

# 23. Why Does Linux Have This Model?

Because Linux is a **multi-user operating system**.

Imagine a server:

```text
Server
 |
 +--- Developer
 +--- Database administrator
 +--- System administrator
 +--- Application service
```

You don't want every identity to have unrestricted access.

Permissions allow Linux to enforce:

```text
Who?
 ↓
Can do what?
 ↓
To which resource?
```

---

# 24. File Ownership Example

Suppose:

```text
database.conf
```

belongs to:

```text
root
```

and has restrictive permissions.

A normal user might try:

```bash
cat database.conf
```

and receive:

```text
Permission denied
```

Why?

Because Linux checked:

```text
Who are you?
      ↓
student

Who owns the file?
      ↓
root

What permissions does student have?
      ↓
No permission
```

Therefore:

```text
Permission denied
```

---

# 25. What Is `Permission Denied`?

This is one of the most common Linux errors.

Example:

```text
bash: ./script.sh: Permission denied
```

It generally means:

> Linux's permission/security rules do not allow the requested operation for your current identity.

Don't automatically assume something is broken.

Often:

```text
Permission denied
```

means:

```text
Linux is correctly enforcing permissions.
```

---

# 26. `chmod` — Change Permissions

Suppose you have:

```text
script.sh
```

and it doesn't have execute permission.

You can change permissions using:

```bash
chmod
```

`chmod` means:

> **change mode**

For example:

```bash
chmod +x script.sh
```

This adds execute permission.

Conceptually:

```text
Before
rw-

After
rwx
```

---

# 27. What Does `+x` Mean?

Break this down:

```bash
chmod +x script.sh
```

```text
chmod
 ↓
change permissions

+x
 ↓
add execute permission

script.sh
 ↓
target file
```

So:

> Add execute permission to `script.sh`.

---

# 28. `chmod` Can Be More Specific

You can specify who gets the permission.

For example:

```bash
chmod u+x script.sh
```

Here:

```text
u = user/owner
+x = add execute
```

So:

> Add execute permission for the owner.

Other useful symbols:

```text
u = user/owner
g = group
o = others
a = all
```

---

# 29. `chown` — Change Ownership

Suppose a file belongs to:

```text
student
```

but you want it owned by:

```text
admin
```

You can use:

```bash
chown
```

which means:

> **change owner**

Example:

```bash
chown admin notes.txt
```

Conceptually:

```text
Before:
Owner = student

After:
Owner = admin
```

Changing ownership generally requires elevated privileges.

---

# 30. Changing Group Ownership

You can also change the group.

For example:

```bash
chown student:developers notes.txt
```

means approximately:

```text
Owner = student
Group = developers
```

So:

```text
student:developers
```

means:

```text
user : group
```

---

# 31. What Is `sudo`?

Now we come to an extremely important command:

```bash
sudo
```

It allows an authorized user to run a command with elevated privileges.

For example:

```bash
sudo dnf update
```

Conceptually:

```text
student
   |
   | sudo
   ↓
Run command with elevated privileges
```

The exact privileges depend on the system's configuration.

---

# 32. Why Do We Need `sudo`?

Suppose you're logged in as:

```text
student
```

but you need to perform an administrative task.

Instead of logging completely into `root`, you can use:

```bash
sudo command
```

for an individual command.

This is safer and gives better control over administrative actions.

---

# 33. `sudo` vs `root`

Think:

```text
Normal user
     |
     +--- normal commands
     |
     +--- sudo → authorized administrative command
```

versus:

```text
root
 |
 +--- broad administrative privileges
```

In professional Linux administration, you will frequently see:

```bash
sudo ...
```

rather than permanently working as root.

---

# 34. Important: `sudo` Doesn't Magically Give Everyone Access

The system controls who is allowed to use `sudo`.

So:

```text
student
   ↓
sudo
   ↓
Linux checks authorization
   ↓
Allowed?
   ├── Yes → command runs
   └── No  → permission denied
```

---

# 35. A Simple Permission Scenario

Imagine:

```text
project/
└── secret.txt
```

Ownership:

```text
Owner = admin
Group = admins
```

Permissions:

```text
-rw-------
```

Meaning:

```text
Owner:
read ✓
write ✓

Group:
read ✗
write ✗

Others:
read ✗
write ✗
```

If `student` tries:

```bash
cat secret.txt
```

Linux checks the permissions.

`student` isn't the owner and isn't given access.

Result:

```text
Permission denied
```

---

# 36. Why Groups Are So Useful

Instead of doing:

```text
Alice → permission
Bob → permission
Charlie → permission
David → permission
```

you can do:

```text
developers
    |
    +--- Alice
    +--- Bob
    +--- Charlie
    +--- David
```

Then give:

```text
developers → permission
```

Now all members can receive the appropriate access.

This is one reason groups are fundamental to Linux administration.

---

# 37. A Very Important Mental Model

Whenever Linux decides whether something is allowed, start thinking:

```text
WHO?
 ↓
Which user am I?

WHAT?
 ↓
What resource am I trying to access?

OWNER?
 ↓
Who owns it?

GROUP?
 ↓
Which group owns it?

PERMISSIONS?
 ↓
What r/w/x permissions exist?

RESULT?
 ↓
Allowed or denied?
```

That mental model will help you understand most basic Linux permission problems.

# 38. Hands-On Exercise

Let's practice.

Create a directory:

```bash
mkdir permissions-lab
cd permissions-lab
```

Create a file:

```bash
touch test.txt
```

Check it:

```bash
ls -l test.txt
```

You'll probably see something similar to:

```text
-rw-r--r-- 1 student student 0 test.txt
```

Now add some content:

```bash
echo "Permission test" > test.txt
```

Read it:

```bash
cat test.txt
```

Now remove the owner's write permission:

```bash
chmod u-w test.txt
```

Check:

```bash
ls -l test.txt
```

The permissions should change.

Then try:

```bash
echo "New content" > test.txt
```

You should get a permission-related error if you're operating as the file owner and the write permission was successfully removed.

Then restore it:

```bash
chmod u+w test.txt
```

Try again:

```bash
echo "New content" > test.txt
```

It should work.

---

# 39. Another Exercise — Execute Permission

Create:

```bash
touch hello.sh
```

Put a command inside:

```bash
echo 'echo "Hello Linux"' > hello.sh
```

Try:

```bash
./hello.sh
```

You may get:

```text
Permission denied
```

Why?

Because the file doesn't have execute permission.

Check:

```bash
ls -l hello.sh
```

Then:

```bash
chmod +x hello.sh
```

Now:

```bash
./hello.sh
```

The script can be executed.

---

# 40. One More Important Concept: `./`

When you run:

```bash
./hello.sh
```

the:

```text
./
```

means:

> **from the current directory**

So:

```text
./hello.sh
```

means:

```text
current directory
       ↓
hello.sh
```

This is different from simply typing:

```bash
hello.sh
```

We'll understand **PATH** later, because that's another important Linux concept.
